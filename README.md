# Kaggle Playground Series S6E11 — Predicting Credit Card Fraud

Цель: предсказать вероятность `is_fraud`; метрика — ROC AUC. Соревнование:
https://www.kaggle.com/competitions/playground-series-s6e11/overview

## Структура

- `data/` — локальные `train.csv`, `test.csv`, `sample_submission.csv` (не коммитятся).
- `src/fraud/` — загрузка данных, признаки, обучение и подбор LightGBM.
- `experiments/` — небольшие отчёты о запусках, входят в Git.
- `artifacts/` — OOF, сабмиты и модели, остаются локально.

Данные положи прямо в `data/`. Установка и запуск из корня проекта:

```powershell
python -m venv .venv
.venv\Scripts\python -m pip install -e .
.venv\Scripts\python -m fraud.cli baseline
.venv\Scripts\python -m fraud.cli tune --trials 8
```

`baseline` использует один фиксированный набор параметров. `tune` сначала
проверяет его, затем случайно выбирает ещё семь наборов из заданной сетки.
Каждый набор оценивается на **одних и тех же пяти фолдах** по общему OOF ROC AUC;
лучший повторно обучается на пяти фолдах для сабмита и анализа признаков.
Подбор таким способом — random search; число попыток меняется через `--trials`.
Все попытки и их оценки записываются в `experiments/<run_id>/trials.csv` сразу
после окончания каждой попытки. Подбор может занять заметно больше времени,
чем `baseline`: по умолчанию это 8 × 5 фолдов для сравнения и ещё 5 для сабмита.

При запуске `experiments/latest_report.txt` перезаписывается. В нём видно
загрузку данных, текущий фолд, число деревьев, ROC AUC на валидации и грубую
оценку оставшегося времени. Лимит в 400 деревьев делает первый прогон быстрым;
ранняя остановка может закончить фолд раньше. Время до лимита — верхняя оценка.

Результат: `experiments/<run_id>/summary.json` с ROC AUC по фолдам и общим OOF,
`permutation_mean.csv` с падением ROC AUC при перемешивании одного признака на
валидации, `feature_importance_mean.csv` с gain/split важностью LightGBM и
`tree_nodes.csv` со всеми узлами разбиения деревьев. `split_gain` показывает
выигрыш функции потерь при построении дерева, а не вклад в ROC AUC. Для решения
об удалении признака смотри сначала `permutation_mean.csv`, затем проверяй
отдельным запуском с теми же фолдами:

```powershell
.venv\Scripts\python -m fraud.cli baseline --drop-feature merchant_category
```

После подбора можно повторять эксперименты с лучшими параметрами:

```powershell
.venv\Scripts\python -m fraud.cli baseline --params-from experiments\RUN_ID\summary.json --drop-feature merchant_category
```

## Проверка слабых признаков после первого baseline

У пяти признаков среднее падение ROC AUC при перемешивании было чуть ниже нуля.
Это слабый сигнал: все они использовались в деревьях, а разница мала по
сравнению с шумом. В наборе `weak_ablation_v1` они исключаются **только из
входа модели**, исходные CSV не меняются. Команда сравнит общий OOF ROC AUC с
первым запуском, сохраняя те же параметры и фолды:

```powershell
.venv\Scripts\python -m fraud.cli baseline --feature-set weak_ablation_v1 --compare-to experiments\20261110_123755_baseline\summary.json
```

Разница появится в `experiments/latest_report.txt` и в `comparison` нового
`summary.json`. Если изменение окажется небольшим, стоит проверить признаки
по одному: совместное удаление не показывает вклад каждого по отдельности.

## One-hot для текстовых категорий

Исходные пять категориальных колонок LightGBM умеет обрабатывать напрямую.
Дополнительный режим сохраняет их и добавляет рядом 35 one-hot колонок.
Сравниваем его на тех же фолдах и параметрах:

```powershell
.venv\Scripts\python -m fraud.cli baseline --categorical-encoding onehot --compare-to experiments\20261110_123755_baseline\summary.json
```

## Точные числовые значения как категории

Числовой столбец сохраняется, а рядом появляется его категориальная копия.
`numeric_cat_low` добавляет 9 копий столбцов с не более чем 1000 уникальных
значений в train. `numeric_cat_all` добавляет 13 копий всех небинарных числовых
столбцов. Для 6 бинарных признаков копия не нужна: разбиение по 0/1 уже точно
представляет обе категории.

```powershell
.venv\Scripts\python -m fraud.cli baseline --feature-group numeric_cat_low --compare-to experiments\20261110_123755_baseline\summary.json
.venv\Scripts\python -m fraud.cli baseline --feature-group numeric_cat_all --compare-to experiments\20261110_123755_baseline\summary.json
```

У `account_balance_usd` почти 50 тысяч различных значений вместе с test.
Категориальная копия такого столбца может замедлить модель и плохо обобщаться
на редкие значения. Поэтому сначала проверяем маленький набор, а полный —
отдельным экспериментом. Исходные значения чисел не удаляются.

## Цифры дробной части

`decimal_digits` добавляет отдельные категориальные признаки для десятых и
сотых разрядов исходных дробных столбцов. Одно значение `amount_usd` с
тысячными встречается только в test, а одна сотая `velocity_score` тоже только
в test; учиться на них модель не может. Единичную сотую `merchant_risk_score`
в train также пропускаем как почти постоянный признак. Остальные исходные
признаки сохраняются. Это проверка гипотезы о сигналах в округлении данных:

```powershell
.venv\Scripts\python -m fraud.cli baseline --feature-group decimal_digits --compare-to experiments\20261110_123755_baseline\summary.json
```

`integer_digits` добавляет единицы (`__i0`), десятки (`__i1`), сотни
(`__i2`) и более старшие цифры **целой части** всех 13 небинарных числовых
столбцов. Число разрядов определяется по train и test без использования меток:

```powershell
.venv\Scripts\python -m fraud.cli baseline --feature-group integer_digits --compare-to experiments\20261110_123755_baseline\summary.json
```

`roundness` добавляет для каждого из 13 небинарных числовых столбцов последнюю
цифру, признак окончания на 0 или 5 и число конечных нулей. Последняя цифра
позволяет модели самой проверить 3, 7 или любую другую цифру без заранее
заданного списка «странных» чисел:

```powershell
.venv\Scripts\python -m fraud.cli baseline --feature-group roundness --compare-to experiments\20261110_123755_baseline\summary.json
```

## Дополнительные идеи

`domain_v1` добавляет отношения суммы к балансу и времени, произведения риска
с суммой и скоростью транзакций, логарифмы положительных величин, циклическое
представление часа и дня недели, отношение возраста карты к возрасту клиента и
счётчик рискованных флагов. Это только дополнительные столбцы; исходные 24
сохраняются.

```powershell
.venv\Scripts\python -m fraud.cli baseline --feature-group domain_v1 --compare-to experiments\20261110_123755_baseline\summary.json
```

Группы можно объединять повторением `--feature-group`, но сначала лучше
проверять каждую отдельно. Ручной биннинг пока не добавлен: LightGBM уже
подбирает пороги для чисел, а отдельные логарифмические или квантильные бины
имеет смысл проверять после результатов этих групп.

## После эксперимента со всеми 165 признаками

Общий OOF ROC AUC снизился с 0.946175 до 0.940795, а обучение останавливалось
около 90 деревьев. Десятичные цифры модель не использовала, и многие числовые
категории получили высокий gain без пользы при перемешивании на валидации.
Следующий контролируемый вариант `focused_v1` добавляет к исходным 24 только
три признака: число рискованных флагов, произведение риска продавца и скорости
транзакций, индикатор отсутствия аутентификации. Каждый из них можно проверить
отдельно группами `risk_flag_count`, `risk_x_velocity`, `auth_no_auth`.

```powershell
.venv\Scripts\python -m fraud.cli baseline --feature-group focused_v1 --compare-to experiments\20261110_123755_baseline\summary.json
```

Большая важность в неудачном эксперименте не гарантирует прирост в новом
моделе: она показывает, насколько тот конкретный набор деревьев зависел от
признака. Решение принимаем по OOF ROC AUC нового запуска.

Отрицательное или нулевое падение ROC AUC при перемешивании может быть шумом
или следствием корреляции признаков. Надёжный критерий — изменение общего OOF
ROC AUC после удаления признака. Большие `oof.csv`, пять файлов моделей и
`submission.csv` лежат в `artifacts/<run_id>/` и не входят в Git. Отчёт по
каждому запуску коммитим отдельно.

## Проверка маленьких деревьев

В [обсуждении Kaggle](https://www.kaggle.com/competitions/playground-series-s6e11/discussion/755149)
LightGBM с 4 листьями показал лучший результат, чем с 31 листом, на тех же пяти
фолдах. Наш прежний подбор проверял только 15, 31 и 63 листа. Команда ниже
меняет только число листьев относительно лучшего запуска с 19 признаками:

```powershell
.venv\Scripts\python -m fraud.cli baseline --feature-set weak_ablation_v1 --num-leaves 4 --compare-to experiments\20261110_124709_baseline\summary.json
```

Разница OOF ROC AUC и изменённые параметры сохраняются в `comparison` нового
`summary.json`. Если лучшие итерации упрутся в лимит 400 деревьев, понадобится
отдельный прогон с более высоким лимитом.

Первый прогон с 4 листьями набрал 0.945980, но три из пяти фолдов дошли до
лимита 400 деревьев. Проверка с увеличенным лимитом и той же ранней остановкой:

```powershell
.venv\Scripts\python -m fraud.cli baseline --feature-set weak_ablation_v1 --num-leaves 4 --n-estimators 2000 --compare-to experiments\20261110_124709_baseline\summary.json
```

Если результат улучшится, для чистого сравнения числа листьев проверим также
15 листьев с тем же лимитом 2000.
